## Findings

### SR-01 — Malformed paymaster signatures revert instead of returning signature failure

**Severity:** Low  
**Component:** VerifyingPaymaster  
**Location:** `contracts/src/VerifyingPaymaster.sol:117–119`  
**Blocking for release 0.1.0:** **No**

**Description.** The paymaster checks that the signature is 65 bytes, then calls OpenZeppelin `ECDSA.recover`. Invalid recovery values or noncanonical signatures can make that function revert. Only a structurally acceptable signature recovering to the wrong signer reaches the intended `SIG_VALIDATION_FAILED` result.

**Exploit scenario and required actor.** An untrusted requester can supply a malformed paymaster signature. No malicious root or sponsor is required. This does not authorize sponsorship: validation fails closed.

**Evidence.** The executed test `test_rejectsMalformedTimestampsAndSignature` explicitly changes the signature’s `v` byte to zero and expects a revert. It separately verifies that a well-formed signature from another key returns packed signature failure.

**Impact.** Inconsistent validation behavior can disrupt gas-estimation and admission flows that expect an invalid-signature result rather than a validation exception. A bundle containing such an operation can fail validation, but this is not a demonstrated sponsor-fund drain or session-policy bypass.

**Smallest recommended fix.** Use `ECDSA.tryRecover`; return `_packValidationData(true, validUntil, validAfter)` for either a recovery error or signer mismatch. Update the malformed-signature test accordingly. Malformed structural encoding can remain a separate parsing failure.

### SR-02 — Native-spend protection requires successful initialization

**Severity:** Informational  
**Component:** Calibur ERC-7914 integration / account initialization  
**Locations:** `contracts/lib/calibur/src/ERC7914.sol:26–29,34–65`; `contracts/src/AgentPolicyHook.sol:107–110`  
**Blocking for release 0.1.0:** **No, provided DESIGN’s initialization precondition is maintained**

**Description.** Calibur v1.1.0 grants ERC20ETH an unlimited native allowance until the account explicitly overrides it. The hook meters outgoing call value, not changes in native balance. It therefore cannot detect a native pull made through ERC-7914 during a zero-value call.

**Exploit scenario and required actor.** If initialization omits `approveNative(ERC20ETH, 0)`, an untrusted session with an allowed route to a native-pulling target can cause an unmetered transfer. The root need not be malicious; an incomplete or incorrect initialization is sufficient, together with the callable pull route.

**Evidence.** The executed test `test_I8_control_withoutInitRevocation_erc20EthPullsNativeUnmetered` omits the reset, demonstrates a 50 MNT-equivalent transfer through an etched ERC20ETH stand-in, and checks that recorded MNT usage remains zero. The corresponding matrix tests verify rejection after proper initialization.

The stand-in demonstrates the dependency; it is not evidence that the same stand-in or attack entry exists at the live canonical address.

**Impact.** An account that has only been delegated, but not safely initialized, must not be represented as having the promised native loss bound.

**Smallest recommended action.** Preserve the atomic initialization sequence and verify the zero native allowance before declaring an account initialized. Keep the negative-control test. Do not replace this requirement with sponsor-only admission checks, since a session can execute directly.

This is a documented design prerequisite, not a newly discovered bypass of a correctly initialized account.

### SR-03 — Hook attachment is an account-configuration invariant, not a Calibur guarantee

**Severity:** Informational  
**Component:** Calibur key registration / session provisioning  
**Locations:** `contracts/lib/calibur/src/KeyManagement.sol:23–51`; `contracts/test/hook/CaliburSessionBase.sol:195–208`  
**Blocking for release 0.1.0:** **No**

**Description.** Calibur permits a non-admin key with a zero hook. Registration and settings updates are separate calls. Its new hook validation rejects some invalid nonzero hooks, but does not require this hook, or all five callback flags, for every non-admin key.

An unhooked key can also reach this account’s hook-management methods through ordinary external calls: those methods identify the account by `msg.sender`, and protection against session access comes from the session’s execution hook.

**Exploit scenario and required actor.** The root must first register an unhooked key, detach its hook, or expose a partially completed grant. A malicious holder of that key can then execute without the intended restrictions. A correctly configured non-admin session cannot make those self-call configuration changes itself.

**Evidence.** The test fixture deliberately registers an unhooked control key. The executed matrix tests show that calls rejected for hooked sessions succeed for the control, including a hook-management call in `test_matrix_I3_targetIsHook`.

**Impact.** The account-wide security claim depends on every untrusted key being correctly configured. An inactive hook policy alone does not protect a key that never calls the hook.

**Smallest recommended action.** Implement and retain the specified atomic grant sequence—register, attach non-admin settings with the correct hook, and set policy—with failure propagation. Later SDK acceptance must cover partial grants and reject unsafe key configurations.

No Calibur fork is recommended for this checkpoint: DESIGN explicitly assigns I6 to provisioning, and the root is fully trusted.

### SR-04 — The invariant campaign does not independently isolate two important guards

**Severity:** Informational  
**Component:** Stateful security testing  
**Locations:** `contracts/test/invariant/AgentPolicyHook.invariant.t.sol:314–335,667–680`; `contracts/src/AgentPolicyHook.sol:94,98,133`  
**Blocking for release 0.1.0:** **No**

**Description.** The mutation observations raised during implementation identify two guards whose removal is caught by deterministic tests but not by the invariant campaign. Source inspection explains why other checks can mask the missing guard:

- Forbidden hook-management actions can still fail the permission allowlist when the explicit `to == hook` rejection is removed.
- Without the entry lock check, nested execution can clear the lock and then cause the outer `afterExecute` to fail with `NotInExecution`. A no-side-effects assertion can consequently still pass, despite admitting the nested execution initially.

**Exploit scenario and required actor.** A future regression could remove an intended defense while the invariant-only job remains green. This is a verification limitation, not a demonstrated exploit against the reviewed implementation.

**Evidence.** All three invariant seeds passed. The invariant re-entry action checks attacker balance changes, whereas the deterministic matrix test also checks the exact inner `Reentrancy` error. The matrix’s hook-target tests similarly check `TargetIsHook`.

The mutation campaign itself was evidence reported during implementation and was not independently rerun.

**Impact.** Passing invariants must not be interpreted as independent mutation coverage of every named guard. The deterministic matrix and attack tests remain necessary.

**Smallest recommended action.** Keep those deterministic tests mandatory. To strengthen the invariant campaign, add a deliberately permitted hook-management attempt and assert the specific nested re-entry rejection, rather than relying solely on final balance conservation.

## Disposition of observations raised during implementation (O1–O6)

### O1 — A pending root-signed batch can execute inside a session call

**Disposition: Not an issue under the stated model; an important composition limitation.**

Calibur root execution has no hook. The hook’s account-level lock therefore does not stop a target from submitting an otherwise valid root-signed batch. Hook-management operations attempted by that batch still encounter `_requireNotExecuting`, but ordinary root-authorized asset movements do not.

At `AgentPolicyHook.sol:438–452`, quote metering charges the positive balance decrease between the outer call’s snapshots. A root-authorized inflow inside that interval can offset the outer call’s outflow.

This does not forge root authority or violate the specified **per-call net** accounting formula. It does mean the hook does not separately attribute the provenance of simultaneous inflows. The root need not be malicious: an outstanding, permissively executable signature can be composed by a malicious target.

Two constraints materially limit the scenario:

1. The prescribed management-signature convention binds the executor to the relayer, not an arbitrary target.
2. A §4.4-conforming launchpad/spender has no arbitrary-call facility for submitting such a batch.

Retain executor binding and avoid broadly relayable root signatures. A stronger requirement to isolate root-originated inflows would require a design change, not merely a claim that the existing lock covers root execution.

### O2 — I8 depends on `approveNative(ERC20ETH, 0)`

**Disposition: Informational, SR-02.**

Confirmed by the executed negative-control test. Proper initialization is part of the security precondition.

### O3 — I6 has no on-chain guard

**Disposition: Informational, SR-03.**

Confirmed. This is explicitly a provisioning invariant. A correctly hooked session cannot detach its own hook, but a root-created unhooked key is unrestricted by this policy layer.

### O4 — Malformed paymaster signatures revert

**Disposition: Low, SR-01.**

Confirmed by the executed test. Failure remains closed; the issue is validation compatibility and predictable error behavior.

### O5 — Two mutations survive the invariant campaign

**Disposition: Informational, SR-04.**

Consistent with the test structure. Deterministic tests provide complementary coverage; the mutation campaign was not rerun.

### O6 — Calibur pays prefund before invoking the validation hook

**Disposition: Not an issue.**

`Calibur.sol:116` calls `_payEntryPoint` before `afterValidateUserOp`. However, the hook’s rejection reverts the enclosing account-validation frame, including the earlier native transfer and the EntryPoint’s resulting deposit update.

The executed tests:

- `test_e2e_noPaymaster_rejected_accountPaysNothing`
- `test_e2e_otherPaymaster_rejected_accountPaysNothing`

use the real EntryPoint implementation and verify that rejection leaves the account balance unchanged. The no-paymaster test also verifies a zero account deposit. Correctly sponsored operations require no account prefund.

## Calibur v1.0.0 → v1.1.0 assessment

The security-relevant source changes are:

| Change | Security assessment and effect on this design |
|---|---|
| Raw root signatures accepted by `validateUserOp` and decoded consistently by `executeUserOp` | Root signatures bypass session hooks by design. Validation still verifies against the account’s root key; merely choosing a 64/65-byte signature does not confer root authority. Execution relies on the trusted EntryPoint validating the operation first. |
| Unregistered wrapped keys return signature failure during UserOp validation | Fail-closed compatibility improvement. Does not let an unknown key reach authorized execution. |
| Non-admin calls to EntryPoint rejected | Closes zero-value routes to account-owned deposit/stake, which call-value metering would not cover. Direct session calls are blocked before target execution. |
| EntryPoint and SenderCreator prohibited as registered keys | Prevents those privileged callers from acquiring direct-execution key authority. The current EntryPoint is trusted; later root changes to it remain root configuration. |
| Public-key encoding validation added | Requires canonical nonzero secp256k1 address encoding and fixed-length P256 public keys. Reduces malformed/alias key representations. Appropriate for the design’s secp256k1 sessions. |
| P256 signatures require exactly 64 bytes | Rejects trailing-data encodings. No material change to the selected session-key scheme. |
| Reserved settings bits rejected; admin flag reduced to one bit | Removes ambiguous privilege encodings. Intended non-admin settings remain valid. |
| Nonzero hooks require deployed code and at least one callback flag | Useful hardening, but not enforcement of I6 or the full `0x1f` mask. `AgentPolicyHook`’s constructor and provisioning requirements supply the stronger condition. |
| Multicall/delegatecall dispatcher removed | Reduces execution surface and removes that batching mechanism. Root management must use Calibur’s batched-call interface. |
| ERC-7914 transient allowance paths removed | Reduces native-transfer surface. |
| ERC20ETH receives default unlimited native allowance, with explicit override support | Material new exposure; addressed only by the required zero-allowance initialization. See SR-02. |
| `updateSalt(uint96)` replaced with monotonically incrementing `updateSalt()` | Prevents selecting a previously used salt prefix through this API, improving domain invalidation. Root-only; clients must use the new selector. It is not a replacement for EntryPoint nonce handling or hook tombstones. |
| ERC-7739 helpers replaced with OpenZeppelin helpers | Changes parsing/hashing implementation. Session signatures still reach the unconditional rejection hook after successful cryptographic verification; invalid signatures fail earlier. The deleted local hash helpers do not create an alternate session authorization path. |
| Root ERC-1271 gains nested PersonalSign acceptance | Broadens root signature compatibility only. Root is intentionally outside session restrictions. |
| `HooksLib.ALL_FLAGS` added | Provides a shared mask; callback selection still depends on the hook address’s low bits. The hook constructor requires all five flags. |
| CaliburEntry inheritance/layout syntax changed | The explicit storage base remains unchanged. This review does not certify migration of existing v1.0.0 account storage to v1.1.0. |
| Example guarded hook relocated and documented as unaudited | Not used by this design; no runtime effect on `AgentPolicyHook`. |

The source still reports EIP-712 version `"1.0.0"`. It must not be treated as sufficient identification of the deployed implementation. The address book records a runtime-code hash, as required by DESIGN.

No additional blocking session-key issue was identified in this incremental diff. The unavailable incremental audit report was not assumed to provide assurance.

## Paymaster port assessment

Apart from SR-01, the reviewed port preserves the intended sponsorship boundary:

- The signed hash covers sender, nonce, initialization and execution calldata, account gas limits, both paymaster gas limits, pre-verification gas, fee fields, chain ID, paymaster, EntryPoint and validity times.
- Excluding the account signature avoids a signing dependency cycle; account authorization remains independently checked by Calibur.
- Exact delegation codehash checking rejects another implementation, including when `initCode` is empty.
- The v0.8.0 base restricts validation to the configured EntryPoint and deposit/stake withdrawals to the owner.
- Returning empty context avoids a post-operation callback requirement.
- Session validation reads the account-associated summary and calldata plus an immutable paymaster address, without introducing a mutable external configuration lookup.

The executed tampering, delegation-binding, validity-window and real-EntryPoint tests support these conclusions. Sponsor request authentication, reservation accounting and signing policy remain outside this checkpoint.

## Limits and release conclusion

This review did not independently verify live deployed bytecode, current balances, current ownership, strict-bundler admission, deployment transactions, or the reported worst-case panic gas figure against a live block limit. It did not rerun the mutation campaign, perform a full audit of Calibur/EntryPoint dependencies, or review the SDK, CLI and sponsor implementation.

The approved security claim remains conditional on correct root provisioning, standard quote tokens, §4.4-conforming spenders and tokens, and correct inventory-release behavior by the root. Limits bound cost basis, not execution price or the market value of attributed positions.

**Release conclusion:** No unresolved High- or Medium-severity contract-security finding was identified at the reviewed SHA. The Low finding is nonblocking for this testnet checkpoint; the initialization and provisioning prerequisites must remain explicit in later integration acceptance.

Not checked: live-chain/fork verification, production operations, or a full dependency audit. Residual risk: unaudited contracts and configuration-dependent guarantees; keep funds small.

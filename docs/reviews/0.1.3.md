## Findings

### SR3-01 — A second sponsor instance releases another instance’s live reservations

**Severity:** Medium  
**Component:** Sponsor startup, ledger, embedded CLI  
**Locations:**  
- `packages/sponsor/src/ledger.ts:117–129` — startup releases every `reserved` entry.
- `packages/sponsor/src/ledger.ts:291–331` — submission continues asynchronously and changes an entry to `submitted` without rechecking its reservation.
- `packages/sponsor/src/main.ts:53` — each submitting instance starts reconciliation.
- `packages/cli/src/cli.ts:280–283` — embedded commands share `<home>/embedded-sponsor.sqlite`.

**Blocking for release 0.1.3:** **Yes**

**Description.** Startup assumes that every reserved-but-not-submitted entry belongs to a terminated process. No exclusive submitting-instance ownership is established before applying that assumption.

This is reachable through ordinary embedded operation: each concurrent submitting CLI command starts its own sponsor on an ephemeral port, but commands using the same home directory share the database. SQLite transactions serialize individual database changes; they do not establish ownership over the asynchronous reserve/sign/broadcast lifecycle.

**Failure scenario under §4.0.** No malicious root, compromised sponsor, or unauthorized signature is required:

1. Embedded instance A admits a request and reserves its worst-case cost.
2. A waits for nonce RPC responses or transaction signing.
3. Instance B starts against the same database.
4. B treats A’s reservation as abandoned, releases it, and records `SUBMISSION_UNAVAILABLE`.
5. A resumes, persists its signed transaction, changes the entry to `submitted`, and broadcasts it.

The transaction is now live with a zero reservation. The recorded error also survives this state transition, so the original caller can receive a refusal despite a transaction having been broadcast.

**Evidence/reproduction.** A targeted test used the existing `FakeChain`, two separate `SponsorStore` connections to the same temporary SQLite file, and two `Ledger` instances:

- A’s signing operation was held behind a promise after reservation.
- Before starting B, usage equalled A’s reserved fee.
- After B started, A’s entry was `released` and usage was zero.
- After A resumed, the fake node had accepted one broadcast, the entry was `submitted`, and both its reserved fee and global recorded usage remained zero.

The final reproduction passed. The promise-controlled pause makes the interleaving deterministic; production also has an asynchronous nonce-read window after reservation.

**Impact.** Outstanding liabilities disappear from budget checks until settlement. Additional requests can be admitted against budget that is already committed, violating the reservation guarantee in DESIGN §5.2. Depending on interleaving, callers can also see incorrect refusal outcomes or competing submissions. The per-instance `#nonceLock` does not serialize independent submitting instances.

This does **not** forge account authorization or bypass the hook. It is a sponsor-accounting and submission-lifecycle defect.

**Smallest recommended fix.** Enforce one active submitting sponsor per persistent database before startup reconciliation and retain that ownership until shutdown. A second embedded invocation should wait or fail explicitly rather than reconcile a live instance’s work. Keep read-only status and intentional recovery operations distinguishable from a second submitting service.

Also recheck the entry’s state before persisting/broadcasting a prepared submission, so a released reservation cannot silently become a live transaction. Add the overlapping-instance regression test; existing concurrency tests exercise requests within one submitting instance, not competing instance startup.

### SR3-02 — SDK transport and sponsor startup errors can expose credentialed URLs

**Severity:** Low  
**Component:** SDK HTTP transport and standalone sponsor error handling  
**Locations:**  
- `packages/sdk/src/executors/http.ts:25–30`
- `packages/sponsor/src/main.ts:74–79,91–92`

**Blocking for release 0.1.3:** **No**

**Description.** The SDK’s HTTP helper states that endpoint URLs never appear in error messages, but its fetch-failure branch interpolates the native error message and retains the original cause. Native fetch errors can contain the complete URL.

Separately, `startSponsor` rethrows startup RPC errors unchanged. The standalone entry point awaits startup without a sanitized top-level error handler. Viem errors can include the RPC URL, including API credentials in its path or query.

**Failure scenario under §4.0.** A legitimate operator configures a credentialed sponsor or RPC endpoint. A rejected URL or startup connection failure occurs. An SDK consumer logs the error, or the standalone sponsor’s unhandled startup error reaches stderr.

No malicious session or compromised account key is required.

**Evidence/reproduction.** Two targeted tests passed using synthetic credential markers:

1. `RelayerExecutor.relayer()` with an HTTP URL containing userinfo returned an error whose `message` contained the synthetic password marker.
2. `startSponsor()` with a paymaster signer enabled and an unreachable RPC URL containing a synthetic path credential returned an error whose string representation contained that marker.

No real credentials were used.

The main CLI’s `run()` error path redacts URLs, so these reproductions do **not** establish a leak through ordinary CLI JSON or human-readable error output.

**Impact.** RPC or sponsor endpoint credentials can reach application logs or standalone-process stderr. No private-key or keystore-password disclosure was demonstrated.

**Smallest recommended fix.** Do not interpolate unsanitized native transport messages into SDK errors. Sanitize errors at the standalone sponsor boundary as well. Ensure retained causes cannot reintroduce the URL when an error is inspected or logged. Test both userinfo credentials and path/query API tokens.

### 2. SDK I6/I7 and initialization preconditions

**Conclusion:** The intended provisioning paths enforce the specified guards; arbitrary trusted-root execution is not a constrained provisioning API.

- `#prepareGrant()` checks hook flags and code before generating the grant.
- Grant settings encode the hook and expiry without the admin bit.
- Register, settings update, and policy initialization share one atomic batch.
- `updateSession()` checks hook validity and requires a hooked non-admin active session.
- `init()` resets `ERC20ETH` native allowance and verifies initialization afterward.
- Ordinary grants require `INITIALIZED`.
- Both executor implementations encode failure-propagating batches.
- Bundler submission refuses session authorizations; sponsor admission independently rejects them.
- Revoke and panic remove authority and write tombstones rather than granting or loosening settings.

`account exec` and low-level root-signed execution can deliberately register an unhooked key or alter initialization state. This is permitted by the fully trusted-root model, not a session bypass. Applications must not describe arbitrary root calldata as preserving I6 automatically.

Evidence includes source tracing, passing policy unit tests, the contract tests above, and inspection of the failed-grant/front-run-authorization fork tests. The recorded completed fork run covers those tests. The independent SDK fork rerun did not finish within its review time bound.

### 3. Sponsor signing and ledger

**Conclusion:** Authentication and signature construction preserve the account-authorization boundary, but accounting conformance fails under overlapping submitting instances.

The reviewed admission paths bind requests to method, sender, key, chain, sponsor, entry, payload, validity, and applicable authorization. They check nonce lanes, registered hooked sessions, expiry, initialization, and their own simulation. Relayer batches bind the executor; paymaster signing covers the specified operation fields and preserves delegate binding.

Within one submitting instance, tests support atomic reservation, account-level exclusivity, idempotency, failed-transaction charging, replacement accounting, restart recovery, and paymaster event-based settlement/expiry release.

Those results do not cover multiple embedded instances. **SR3-01 breaks the reservation lifecycle despite correct individual SQL transactions.** Consequently, the claim that sponsor accounting remains correct across supported embedded usage is not established at this commit.

Known confirmation-depth, oracle-change, cross-key sponsorship, and abandoned-operation limitations remain as assessed above.

### 4. CLI/SDK panic and key handling

**Conclusion:** Panic’s normal execution sequence matches the design; error confidentiality is incomplete.

Panic enumerates registered Calibur keys plus locally known session profiles, constructs revocations/tombstones and deduplicated allowance resets, and leaves inventory reserved. Self-pay uses a root transaction to the account. Undelegation is separate and begins only after phase-one success; authorization uses the self-sent transaction nonce plus one. A subsequent state read checks that undelegation actually applied.

The recorded maximum-size test checks **eight revokes, eight tombstones, and 128 nonzero-to-zero allowance resets**, not merely a successful receipt. It also checks frozen inventory and later-block undelegation. Recorded gas is below the 60 million block limit. Independent contract tests and live panic transaction spot-checks supplement that evidence.

Keystore storage uses encrypted v3 data, exclusive key-file creation, restrictive creation modes, and signer/profile consistency checks. No private-key or password leak was demonstrated. However, **SR3-02 disproves the broader claim that credentialed URLs cannot reach SDK/sponsor errors**.

### 5. E2E results and Sepolia acceptance

**Conclusion:** The examined acceptance tests provide substantive positive and negative evidence, not merely SDK-level rejection or empty gates.

Important checks include:

- Direct fixed-gas transactions bypass SDK and sponsor admission.
- Relayer rejection tests require a mined reverted receipt and the expected decoded error.
- Bundler tests distinguish outer transaction success from `UserOperationEvent.success`.
- Successful bundler steps assert the EntryPoint destination, expected paymaster, operation success, and a validation trace.
- Over-limit BUY tests establish an allowance that makes the forbidden spend otherwise possible.
- Inventory tests include human-owned meme.
- Revocation tests re-register the Calibur key before retesting hook inactivity, separating tombstones from key removal.
- Wrong-paymaster acceptance includes a funded state-override control, avoiding an empty-account prefund failure masking the hook check.
- CI fork gates reject missing, skipped, or empty fork suites.

The recorded completed logs report **335/335 TypeScript tests**, **88/88 E2E tests**, **16 fork files with zero skips**, **249/249 Foundry tests**, and the fixed-seed invariant campaign. These were inspected as recorded evidence, not represented as independent reruns.

The acceptance script and package/deployment inputs are unchanged between `9ae7e1e` and the reviewed commit. Public-RPC checks confirmed the recorded type-4 initialization bundle, a reverted forbidden call, and successful ordered panic transactions followed by empty account code.

These checks support the recorded acceptance claims. They do not prove every guard independently under mutation, nor cover competing embedded sponsor startup.

### 6. Accepted debt

**Conclusion:** The recorded severities remain reasonable for a small-funds testnet POC, subject to the explicit limitations above. None excuses SR3-01.

In particular, sponsor trust for funds does not make incorrect accounting acceptable: the implementation must still honor its own admission and reservation rules during ordinary use.

## Limits and release disposition

This review did not independently rerun the entire strict-Alto E2E suite, the three-seed invariant campaign, or the mutation campaign. Their recorded results were inspected and distinguished from independently executed evidence. The targeted SDK/CLI fork rerun was time-bounded to avoid a prolonged shared-machine workload.

Live verification was a transaction/state spot-check, not a reconstruction of all 62 acceptance transactions, all historical balances, or all deployment ownership/codehash checks. No full dependency audit, production-readiness assessment, gas optimization review, or adversarial public-service load test was performed.

**Release disposition:** fix SR3-01 and verify exclusive submitting-instance behavior plus the existing single-instance recovery tests before approving release 0.1.3. SR3-02 is nonblocking for this testnet release but should be corrected before relying on the SDK or standalone sponsor’s error-confidentiality promise.

The summary counts the two SR3 findings above; unchanged previously accepted debt is assessed separately. Residual risk remains configuration-dependent, unaudited contracts and testnet infrastructure; keep funds small.

## Disposition (after the review)

Both findings were fixed on `release/v0.1.3` after the review:

- **SR3-01 (Medium)** — fixed in #52: one submitting sponsor per database. A sponsor claims an
  exclusive lock on its database before start-up recovery and holds it until it closes, so a
  second sponsor on the same database (including a second embedded CLI command with the same home)
  refuses to start instead of releasing the first one's reservations; a prepared relayer
  transaction is persisted and broadcast only if its entry is still reserved. A regression test
  reproduces the interleaving of two sponsors on one database.
- **SR3-02 (Low)** — fixed in #53: SDK transport errors and standalone sponsor start-up errors
  carry no URL (no native message or cause on transport failures; start-up errors are redacted),
  using URL redaction shared by the SDK, the CLI and the sponsor.

The verdict above applies to `ac975ecbf6f6d30cc8c4b97a520705b5eb5d0c2b`. The fixes are covered by
the release's own review of its final candidate, not by this document.
